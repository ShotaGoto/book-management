# ADR-0001: 技術スタック選定

- **日付:** 2026-05-29
- **ステータス:** 採用済み

## コンテキスト

Salesforce 依存のシステムを刷新する。密結合・高改修コスト・AI 活用時代の柔軟性不足が課題。

## 決定

### フロントエンド

| 項目 | 採用技術 | 理由 |
|---|---|---|
| UI フレームワーク | React | SPA 構成、コンポーネント再利用性、エコシステム |
| CSS | Tailwind CSS | 開発速度、AI 生成コードとの相性 |
| 状態管理 | Zustand | Redux より軽量、Feature 単位で管理しやすい |
| UI 設計 | Atomic Design × Feature-first | 再利用性と機能単位の責務分離を両立 |
| ホスティング | S3 + CloudFront | AWS 統一、低コスト、静的配信 |

### バックエンド

| 項目 | 採用技術 | 理由 |
|---|---|---|
| 言語 | Go | シンプル・高速・AI 時代でも保守しやすい |
| Web フレームワーク | Echo | 軽量、高速、構造が理解しやすい |
| API 構成 | SPA + API サーバ完全分離 | 責務分離、将来のモバイル展開に対応 |
| API ドキュメント | Swagger UI + swaggo/swag | Go コメントから自動生成 |
| バリデーション | go-playground/validator | Go 界隈で標準的 |
| ログ | rs/zerolog | 高速・構造化ログ |
| DB アクセス | sqlc | ORM を避け SQL を明示的に書く |

### データベース

| 項目 | 採用技術 | 理由 |
|---|---|---|
| RDBMS | PostgreSQL | 実績・拡張性・SQL 機能の豊富さ |

### インフラ / DevOps

| 項目 | 採用技術 | 理由 |
|---|---|---|
| コンテナ実行 | ECS | AWS 統一、運用負荷を抑える |
| CI/CD | ECS ベースのデプロイ | コンテナ化との親和性 |
| 環境変数 | ローカル `.env` + godotenv / 本番 ECS Task 定義 | ローカルと本番で責務分離 |
| ビジュアルリグレッションテスト | Chromatic | Storybook 連携、UI 差分検知が容易 |

## アーキテクチャ思想

1. **Salesforce 依存からの脱却** — Web 技術へ統一、API 中心設計
2. **AI がコードを書く前提** — 暗黙ルールが少なく、ディレクトリ責務が明確。巨大 ORM 回避、SQL を明示的に書く
3. **AWS への統一** — 学習対象の絞り込み、IAM・監視の一元化
4. **長期運用可能性を優先** — チームが変わっても 5 年後もメンテ可能。React / Go / PostgreSQL という標準寄りの構成

## 結果

`frontend/`(React + Vite) と `backend/`(Go + Echo) のモノレポ構成で実装。
